# Example: MID on the nRF5340

Concrete reference for implementing MID on Nordic's nRF5340. The nRF5340 was chosen because it has a USB-FS peripheral, a capable application core (Cortex-M33 @ 128 MHz), and ships with the Zephyr USB-D stack — all the moving parts MID needs are in place, and there's nothing exotic about the choice. Any USB-capable MCU with a Bulk endpoint pair would do.

The example tracks the same hypothetical sensor pack as [`generic-device.md`](generic-device.md): one tool, one resource, optional interrupt notifications.

## What you need

- nRF5340 DK or a custom board using the nRF5340.
- nRF Connect SDK ≥ 2.6 (Zephyr 3.6+).
- A host running Linux, Windows 10+, or macOS 11+.
- The MCP server library of your choice for the device — for portability, the example assumes a small in-house dispatcher rather than a specific SDK. Anything that can take a JSON-RPC request and return a JSON-RPC response will work.

## SoC notes (the parts that matter)

- The nRF5340 USB peripheral is **Full-Speed only**. Bulk `wMaxPacketSize` therefore caps at 64 bytes, and the spec's length-prefixed framing (`SPEC.md` §7) does the heavy lifting for large messages.
- The application core has plenty of RAM (512 KB) for buffering MCP messages up to the recommended 256 KB ceiling.
- The network core is irrelevant to MID; this is purely an application-core problem.
- USB endpoints on the nRF5340: USBD has 8 IN + 8 OUT endpoints plus EP0; allocating one Bulk pair + one Interrupt-IN is trivial.

## Zephyr configuration

In your `prj.conf`:

```kconfig
CONFIG_USB_DEVICE_STACK=y
CONFIG_USB_DEVICE_PRODUCT="MID Sensor Pack"
CONFIG_USB_DEVICE_VID=0x1915          # Nordic VID, replace with your own
CONFIG_USB_DEVICE_PID=0x53A0          # your assigned PID
CONFIG_USB_DEVICE_BOS=y               # required for BOS Platform Capability
CONFIG_USB_DEVICE_MS_OS_DESC=y        # for WinUSB auto-binding (SPEC §9)
CONFIG_USB_COMPOSITE_DEVICE=y         # if you also expose CDC etc.
CONFIG_USB_REQUEST_BUFFER_SIZE=4096   # for the Tier-2 capability index
```

You'll need a small custom class driver (Zephyr does not ship one for MID, since the class doesn't exist yet). The custom-class hook in Zephyr's USB-D stack is well-documented; you register descriptor callbacks for the MID functional descriptor, the BOS Platform Capability, and a control-request handler for `GET_CAPABILITY_INDEX`.

## Wiring up the descriptors

In firmware, declare the MID functional descriptor (§5) as a packed struct in flash:

```c
struct __packed mid_functional_desc {
  uint8_t  bLength;            // 32
  uint8_t  bDescriptorType;    // 0x24
  uint8_t  bDescriptorSubType; // 0x01
  uint16_t bcdMID;             // 0x0100
  uint8_t  bmCapabilities;     // 0b00110001
  uint16_t wToolCount;
  uint16_t wResourceCount;
  uint16_t wPromptCount;
  uint8_t  descriptorCacheHash[16];
  uint8_t  bDataEndpointIn;    // 0x82
  uint8_t  bDataEndpointOut;   // 0x02
  uint8_t  bNotifyEndpointIn;  // 0x83
  uint8_t  bIndexMaxSize;      // 1 (≤256 B index for this device)
};

static const struct mid_functional_desc mid_func = {
  .bLength = sizeof(struct mid_functional_desc),
  .bDescriptorType = 0x24,
  .bDescriptorSubType = 0x01,
  .bcdMID = sys_cpu_to_le16(0x0100),
  .bmCapabilities = 0x31,
  .wToolCount = sys_cpu_to_le16(1),
  .wResourceCount = sys_cpu_to_le16(1),
  .wPromptCount = 0,
  .descriptorCacheHash = { /* generated at build time, see below */ },
  .bDataEndpointIn  = 0x82,
  .bDataEndpointOut = 0x02,
  .bNotifyEndpointIn = 0x83,
  .bIndexMaxSize = 1,
};
```

The `descriptorCacheHash` should be computed offline by a small build script that canonicalises the full MCP capability set (`SPEC.md` §6.4) and writes the low 128 bits of SHA-256 into a generated header file. Recompute only when the schemas change; this keeps host caches valid across firmware bumps that don't touch capabilities.

## BOS Platform Capability

In Zephyr, you supply BOS descriptors via the `usb_bos_register_cap()` API. The MID Platform Capability is a 28-byte struct (`SPEC.md` §10). Register it once at boot. The MS OS 2.0 Platform Capability is a parallel registration, used by Windows to auto-bind WinUSB — Zephyr has examples in its WebUSB sample.

## Control request handler

Hook `GET_CAPABILITY_INDEX` (`bRequest = 0x01`) in your class-specific control handler. The handler returns the CBOR-encoded capability index from §6.2.

Because the index is bounded by `bIndexMaxSize × 256` and this device has only two items, a static const buffer baked at build time is fine. Larger devices should generate it at boot from the same MCP schema definitions the dispatcher uses, to keep the index and the live `tools/list` response in sync.

## Endpoint allocation

A minimal `usb_ep_cfg_data` array:

```c
static struct usb_ep_cfg_data mid_eps[] = {
  { .ep_cb = mid_bulk_out_cb,     .ep_addr = 0x02 },
  { .ep_cb = mid_bulk_in_cb,      .ep_addr = 0x82 },
  { .ep_cb = mid_interrupt_in_cb, .ep_addr = 0x83 },
};
```

Bulk endpoints use the standard Zephyr `usb_transfer()` flow; you wrap it with the 4-byte length prefix per `SPEC.md` §7.

## Hooking the MCP dispatcher

Implement a tiny framer:

```c
static int read_framed_message(uint8_t *buf, size_t cap, size_t *out_len) {
  uint8_t hdr[4];
  int n = usb_transfer_sync(MID_BULK_OUT, hdr, sizeof hdr, USB_TRANS_READ, K_FOREVER);
  if (n != 4) return -EIO;
  uint32_t len = sys_get_le32(hdr);
  if (len > cap) return -EMSGSIZE;       // §7: respond with -32600 at the JSON layer
  n = usb_transfer_sync(MID_BULK_OUT, buf, len, USB_TRANS_READ, K_FOREVER);
  if (n != (int)len) return -EIO;
  *out_len = len;
  return 0;
}
```

Symmetric `write_framed_message()` on `MID_BULK_IN`. Hand the parsed JSON-RPC request to your MCP dispatcher; write the response back framed.

The MCP dispatcher itself is unchanged from whatever you'd run over stdio — that's the point of the MCP-native binding. If you're using a third-party MCP library that assumes a streaming socket, the simplest adapter is a pair of in-memory buffers: framer pushes bytes in, dispatcher pulls JSON out.

## Notifications on Interrupt-IN

When a resource changes (sensor reading drift, for instance), the device pushes:

```json
{"jsonrpc":"2.0","method":"notifications/resources/updated",
 "params":{"uri":"live://sensors"}}
```

framed per §7 (length-prefixed UTF-8), onto endpoint `0x83`. The Zephyr USB-D stack handles the polling rate; `bInterval = 16` ms is a reasonable default.

Per `SPEC.md` §8, only notifications (no requests, no responses) go on Interrupt-IN.

## Host-side smoke test (Linux)

Quick sanity check using libusb from a Python script:

```python
import usb.core, struct, json
dev = usb.core.find(idVendor=0x1915, idProduct=0x53A0)
dev.set_configuration()
# Issue GET_CAPABILITY_INDEX (control transfer on the MID interface, e.g. interface 1)
data = dev.ctrl_transfer(0xA1, 0x01, 0, 1, 256)
print("capability index (cbor):", data.tobytes().hex())

# Initialize over Bulk
init = json.dumps({"jsonrpc":"2.0","id":1,"method":"initialize","params":{
    "protocolVersion":"2025-06-18", "capabilities":{},
    "clientInfo":{"name":"smoke","version":"0"}}}).encode()
dev.write(0x02, struct.pack("<I", len(init)) + init)
hdr = dev.read(0x82, 4).tobytes()
(rlen,) = struct.unpack("<I", hdr)
body = dev.read(0x82, rlen).tobytes()
print("initialize response:", body.decode())
```

(Requires you to have detached any kernel driver, or matched the interface to the WinUSB / libusb backend on Windows — MS OS 2.0 should already arrange that.)

## Performance envelope (Full-Speed)

- USB-FS theoretical Bulk throughput is ~1 MB/s sustained; in practice you'll see 300–600 KB/s.
- A 4 KB Tier-2 capability index transfers in ~10 ms.
- An MCP `tools/list` response of 50 KB transfers in ~150 ms.
- Per-message latency floor is ~1 ms (one USB frame).

If you need more throughput, the nRF5340 caps at USB-FS; for High-Speed Bulk, jump to an STM32H7 or similar. The spec is unchanged across speeds — only `wMaxPacketSize` and effective throughput move.

## What this example deliberately doesn't do

- No DFU. Add it as a separate interface (Zephyr's USB DFU sample) if you want field-updatable firmware. MID is orthogonal.
- No authentication. Add a `session/authenticate` tool inside the MCP server if you need it; `SPEC.md` §13 explains the threat model.
- No power management cleverness. Standard USB suspend/resume applies; your MCP dispatcher should be idempotent across suspend cycles.
